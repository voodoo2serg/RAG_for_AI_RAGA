# RAGA: техническая концепция управления контекстом и сохранения источников

**Редакция:** Community Core · **Проверено:** 20 ноября 2026 года · **Основание:** опубликованный исходный код и архитектурные документы предшествующего проекта.

## 1. Главная идея

Контекстное окно ИИ не должно превращаться в архив всей жизни проекта. В длинных чатах перемешаны действующие правила, принятые решения, нерешённые задачи, черновики, повторы, ошибочные предположения и промежуточные рассуждения. При переходе к другой модели эти сведения часто приходится собирать заново.

**RAGA отделяет долговременную память проекта от небольшого рабочего контекста модели.** Полный источник хранится независимо. Пользователю или агенту передаётся сначала краткое состояние работы; за дополнительными доказательствами можно обратиться к релевантным фрагментам, а при необходимости — открыть полный исходный диалог.

> **Принцип: большой и проверяемый архив знаний при минимально необходимом текущем контексте. Сокращение контекста не должно уничтожать путь к оригинальному источнику.**

Это пока прежде всего **архитектурный принцип**, а не доказанный показатель экономии токенов: опубликованная редакция ограничивает число и длину передаваемых фрагментов, но не реализует самостоятельный адаптивный оптимизатор токен-бюджета.

## 2. На какие решения ориентировались

В исследовательских материалах исходной RAGA от 28 апреля 2026 года сравнивались следующие продукты и библиотеки. Это **референсы для анализа задач и подходов**, а не источники заимствованного кода и не зависимости публичного репозитория.

| Референс | Сильная сторона | Какой вывод сделан для RAGA |
| --- | --- | --- |
| Dify | Сборка ИИ-приложений и рабочих сценариев | RAGA должна поставлять переносимый контекст, а не дублировать конструктор агентов |
| AnythingLLM | Простое локальное использование и документные чаты | Развёртывание должно быть доступно одному пользователю |
| RAGFlow | Работа с документами и отслеживаемыми ответами | Результат поиска должен вести к исходному тексту |
| Khoj | Персональная база знаний и доступ из разных инструментов | Пользователь должен владеть долговременной памятью |
| Open WebUI | Удобная работа с локальными моделями | ИИ можно подключать локально, без облачного ключа |
| LangChain, LlamaIndex, Haystack | Компонуемые RAG-механизмы | Нужен открытый API для других приложений |

Отличие RAGA задумано не как «ещё один чат с файлами», а как **система непрерывности работы**: диалог преобразуется в контролируемые человеком знания, правила, скиллы, решения и тикеты.

## 3. Что находится внутри публичной системы

\`\`\`text
Чаты / TXT / MD / JSON / JSONL / CSV / LOG / ZIP
                      |
          Импорт с сохранением оригинала
                      |
           Проект -> Сессия -> Фрагменты
                     /   \
     Правила / скиллы     Поиск по фрагментам
     Решения / тикеты     BM25 + локальные векторы
                     \   /
           Человеческая проверка
                      |
         Актуальное состояние проекта
                      |
      Краткий контекст / JSON-архив / API
                      |
          Другая модель или агент
\`\`\`

**Стек публичной версии:** Python, FastAPI, SQLite, простой веб-интерфейс и необязательная Ollama. В ранней архитектуре рассматривались Next.js, PostgreSQL с pgvector, Redis/Celery и объектное хранилище. Это история проектирования, а не обязательный стек нынешнего Community Core.

| Модуль | Назначение |
| --- | --- |
| \`api.py\` | Проекты, сессии, ручное управление знаниями, экспорт и восстановление |
| \`knowledge.py\` | Импорт, фрагментация, лексический поиск, ответы локальной модели |
| \`semantic.py\` | Эмбеддинги через Ollama, косинусная близость, гибридный поиск |
| \`extract.py\` | Извлечение кандидатов в правила, скиллы, решения и тикеты |
| \`webui.html\` | Локальный пользовательский интерфейс |
| \`backend/tests/\` | Проверки алгоритмов и API |

Таблицы SQLite: \`projects\` (проекты), \`sessions\` (оригинальные тексты), \`items\` (объекты знаний), \`chunks\` (фрагменты) и необязательная \`chunk_vectors\` (векторы). У фрагмента сохраняются идентификатор исходной сессии, порядковый номер и название источника.

## 4. Какие данные и сервисы обрабатываются

Публичная версия принимает текст напрямую, через API или из файлов UTF-8: \`.txt\`, \`.md\`, \`.json\`, \`.jsonl\`, \`.csv\`, \`.log\`, а также ZIP-архивов с поддерживаемыми текстами. Для JSON предусмотрено извлечение строк из полей \`content\`, \`text\`, \`message\` во вложенных структурах. Установлены ограничения размеров; импорт синхронный.

В проектной истории рассматривались чат-архивы, Telegram, GitHub, внешние агенты, API совместимых моделей, локальные модели и S3-совместимые хранилища. **Это перечень изучавшихся вариантов**, а не список готовых интеграций публичной редакции. Готовы универсальный HTTP API, файловый импорт и необязательная локальная Ollama.

Предусматривались два режима получения памяти: историческая загрузка архива и поток событий работающего агента. В Community Core реализованы загрузка текста/файлов и приём отдельного текста через API; готового непрерывного приёмника событий агентов нет.

## 5. Как устроены индексация и векторизация

### Разбиение источников

\`knowledge.py\` делит текст по абзацам, большие фрагменты дробит и допускает перекрытие соседних частей. Базовые настройки — около **1100 символов на фрагмент** и **150 символов перекрытия**. Это именно символы, не токены; из-за границ абзацев фактическая длина может отличаться. Фрагмент хранит ссылку на оригинальную сессию.

### Лексический поиск

По умолчанию используется ранжирование, близкое к **BM25**: учитываются частоты слов в фрагменте, встречаемость по корпусу и длина документа. Поиск ограничен выбранным проектом и возвращает несколько наиболее подходящих фрагментов, обычно **восемь**. Вместе с текстом возвращаются ID сессии и фрагмента, порядковый номер, источник и оценка релевантности.

### Семантический поиск

При подключении локальной **Ollama** текст передаётся модели эмбеддингов, например \`nomic-embed-text\`, и преобразуется в числовой вектор. Векторы сохраняются в SQLite в JSON-формате. При запросе строится вектор вопроса, после чего вычисляется **косинусная близость** с сохранёнными векторами.

Гибридный режим использует простую формулу: **0,7 × семантический показатель + 0,3 × нормированная лексическая релевантность**. Это не универсально откалиброванная модель ранжирования. Векторный поиск здесь выполняется перебором, без специализированного ANN-индекса, поэтому рассчитан на небольшие корпуса.

Векторизация выполняется **по отдельному запросу к API \`/vectorize\`**, а не автоматически при загрузке.

**Граница открытого кода:** закрытый исследовательский модуль RAGA-64 не включён. Публичная версия применяет стандартные эмбеддинги и косинусное сходство, без специальных закрытых методов.

## 6. Минимальный контекст с полным путём к источнику

Самая важная архитектурная особенность — **трёхуровневое раскрытие знаний**.

| Уровень | Что получает потребитель | Где реализовано |
| --- | --- | --- |
| **А. Рабочая память** | Действующие правила, решения, тикеты, скиллы и заметки | \`GET /api/projects/{id}/continuity\` — краткий Markdown; сейчас не более 50 заголовков на категорию |
| **Б. Доказательства** | Фрагменты по конкретному вопросу | \`POST /api/projects/{id}/retrieve\` или \`/semantic-search\` — релевантные отрывки с ID и оценками |
| **В. Оригинал** | Исходная переписка или полный переносимый архив | \`GET /api/projects/{id}/sessions/{session_id}\` и \`/backup\` |

Сейчас переход **А → Б → В** доступен как последовательность запросов пользователя или внешнего агента. **Автоматического диспетчера поэтапного раскрытия пока нет.**

Для необязательных ответов локальной модели маршрут \`/ask\` передаёт ограниченное количество найденных фрагментов; каждый обрезается до **1400 символов** в сформированном запросе. Модели предлагается ссылаться на пронумерованные отрывки и признавать недостаточность источников. Это позволяет не загружать в её окно весь архив, но не гарантирует точный токен-бюджет или достоверность ответа.

**Пример:** из длинного обсуждения выделено правило «Перед публикацией проверить цитирования». В новом сеансе агенту можно передать только правило. Если возникает вопрос, почему оно было принято, запрашивается конкретный фрагмент. Если нужна вся аргументация, открывается оригинальный чат. Содержание не теряется, но не занимает контекст постоянно.

## 7. Почему важно участие человека

В RAGA правило, тикет, решение или скилл — отдельный управляемый объект. Пользователь может создать его вручную, скорректировать текст, назначить статус или удалить. Автоматическое извлечение в открытой версии основано на словарных эвристиках и создаёт **кандидатов**, а не установленные факты. Скилл можно выгрузить как Markdown в форме \`SKILL.md\`; полноценной среды исполнения скиллов пока нет.

Такой подход нужен в исследовательских, редакционных и гуманитарных процессах, где особенно важны оригинальная формулировка, различение факта и интерпретации, возможность воспроизвести основание решения.

В исходной архитектуре выделялись пять уровней знаний: **секреты, правила, скиллы, разговоры, техническая история**. Также проектировались очередь подтверждения, контроль источников, напоминания агентам и проверка потери контекста. Эти механизмы нельзя целиком считать реализованными в Community Core: текущая версия хранит типизированные записи и связи с сессиями, но не реализует все пять уровней разграничения доступа.

## 8. Открытость и переносимость

Независимость от поставщика ИИ достигается не обещанием работы со всеми сервисами без настройки, а **владением собственными данными и стандартными интерфейсами**: JSON для полного архива, Markdown для рабочего контекста и скиллов, HTTP/OpenAPI для доступа приложений.

Публичное ядро не требует внешнего облачного ИИ для базового режима. Ollama может быть включена локально по желанию. Любой сторонний агент, способный обращаться к API или принимать Markdown, потенциально может использовать RAGA как внешний слой памяти — с учётом собственных ограничений такого агента.

## 9. Ограничения и технические риски

Это **персональная локальная редакция**, а не готовый многопользовательский облачный сервис. Нет полноценной матрицы прав, промышленного ограничения запросов, очереди обработки больших архивов, высокопроизводительного векторного индекса, готового парсера PDF/DOCX и обязательной проверки фактов. Не стоит открывать API напрямую в интернет. Общий API-ключ не заменяет пользовательскую авторизацию.

Импортированные чаты могут содержать персональные данные, секреты или вредоносные инструкции; источники не следует автоматически считать доверенными. Полные резервные копии требуют защиты.

**Процент экономии токенов и прирост качества пока не измерены.** Для таких утверждений нужны воспроизводимый корпус, базовый сценарий сравнения, единый токенизатор, оценка качества ответов и тесты восстановления источников.

## 10. Направления дальнейшей разработки

Приоритеты для реализации исходной концепции полностью: токен-бюджеты, компактные утверждения с доказательными ссылками, автоматический механизм раскрытия **А → Б → В**, протокол оценки релевантности и противоречий, версионирование скиллов, фоновые очереди импорта и масштабируемый векторный индекс. Отдельно нужен контроль того, что сокращённый контекст не потерял существенную для задачи информацию.

**Итоговый принцип RAGA: передать модели минимально достаточный и проверяемый контекст, сохранив возможность получить любой существенный фрагмент и полный оригинал.**
